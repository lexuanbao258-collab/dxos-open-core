# ADR-0024 — Opaque Workflow CREATE + database-verifiable SQL caller attestation

No migration, executable function, key, database credential, Java code, HTTP registration or staging/shared-Supabase access is created by this ADR. ## 1. Source evidence and decision C3: CREATE without an unauthorized collision read

**Exact source behavior:** `WorkflowRuntime.createInstance` probes `persistence.loadInstance(instanceId)` *before* loading the definition. The public `WorkflowPersistencePort.loadInstance` must return the **real authoritative instance** for an existing ID. If the new server-generated ID happens to collide with a private instance belonging to another tenant, this collision probe either reads hidden data or a security wrapper changes Core read semantics by fabricating a result. [WorkflowRuntime.java](../../backend/src/main/java/com/tricore/dxos/core/workflow/WorkflowRuntime.java), [WorkflowPersistencePort.java](../../backend/src/main/java/com/tricore/dxos/core/workflow/WorkflowPersistencePort.java).

**Chosen gateway-only design: C3 (NOT C1 or C2).** The secured HTTP CREATE flow does **not call** `WorkflowRuntime.createInstance` or its `loadInstance(newId)` probe. Instead `AuthorizedWorkflowService.create` privately executes these steps:
1. Authenticate JWT through the trusted `CurrentPrincipal.requireVerified()` boundary. Validate caller shape and exact `workflow:create` authority. The HTTP body has **no instanceId field** and must reject an unexpected instanceId, not ignore it.
2. Generate exactly one opaque ID from the current `WorkflowInstanceIdGenerator.nextId()` (24 `SecureRandom` bytes -> base64url, `wf_` prefix); the service owns it. Generate it **once for this attempt**; never accept a client-supplied replacement. This creates no ownership/visibility proof.
3. Under an operation+resource+definition-bound authorized *CREATE* scope, call `WorkflowPersistencePort.loadDefinition(exactId, exactVersion)` using the **internal guarded** SQL path. Only the signed resource, tenant binding and exact version are eligible; it must not become a public definition-listing endpoint.
4. Construct `WorkflowInstance.notStarted(serverId, authoritativeDefinition, exactResourceReference, clock.instant())`. Its Core invariants remain authoritative: `NOT_STARTED`, version zero, exact initial state, `createdAt == updatedAt` at nanosecond precision.
5. Call **only** `WorkflowPersistencePort.createInstance(initial)` through the private guarded adapter. This **write method** on its own checked physical JDBC connection locks the tenant guard `FOR SHARE`, independently authenticates the CREATE capability, revalidates active tenant membership, exact operation grant and exact active definition binding, re-derives authoritative initial state, and performs one globally unique `instance_id` INSERT with confirmed COMMIT *before returning*. Database uniqueness is the **final collision arbiter**.
6. If known-rollback duplicate key / `INSTANCE_ALREADY_EXISTS` occurs, do **not** SELECT or return the colliding instance. Map to a **non-identifying internal failure** (or review a bounded **new-attempt only after confirmed rollback**, but MVP default is no automatic retry). Never map this hidden collision to a caller-visible 409 with collided ID. `COMMIT_OUTCOME_UNKNOWN` is never automatically retried, and a lost response requires an independently approved reconciliation/idempotency contract.
7. Return an authorized-created instance only after confirmed durable COMMIT; no preliminary protected snapshot escapes. The old unregistered `WorkflowController` must be replaced/adapted before registration, never simply injected with unguarded `WorkflowRuntime`.

**Why C3:** No changed public Core signatures/semantics, no fake `WorkflowInstance`, no hidden `loadInstance` probe, retains immutable Domain + atomic port write, complies with ADR-0023 Option A. It **does intentionally bypass Runtime's CREATE orchestration at the trusted Gateway**, so it needs separate error-precedence/domain-equivalence review: currently Runtime checks instance duplicate before definition missing, while C3 loads definition first. This difference is *internal only for a server-generated ID* and must not be silently represented as exact general-Core error precedence equivalence. Existing direct Core callers are unchanged. Do not claim that the C1 core modification was approved by Yến's D1–D5.

**Rejection tests:** force the ID generator to return an already persisted ID in another tenant; fail closed with no snapshot/history query or partial insert and no external existence oracle; missing/hidden definition binding and forbidden CREATE return protected classification; concurrent generated duplicate race and unknown-commit injection preserve no partial history/no retry; the backend must have no callable production HTTP path into `WorkflowRuntime.createInstance`.

## 2. Chosen SQL provenance architecture: HMAC-SHA-256 v1 (subject to independent approval)

### 2.1 Scope and exclusions

**Goal:** A principal holding **only** the online `dxos_wf_runtime` PostgreSQL credentials and arbitrary SQL ability must neither query protected V3/V5 tables directly nor forge another actor/action/target by invoking `SECURITY DEFINER` functions. Every allowed function uses an operation-specific proof made by the **trusted post-JWKS Java boundary**, independent of runtime DB credentials.

**Chosen cryptographic primitive for the design:** `HMAC-SHA-256` over **strictly canonical binary framing**. PostgreSQL 17's optional `pgcrypto.hmac(data BYTEA, key BYTEA, 'sha256')` may support verification; ***extension availability, actual namespace, privileges and secure equality comparison are not assumed***. The Java signer uses Java `Mac` `HmacSHA256` with a dedicated, unpredictable **32-byte or stronger random secret**, provisioned out of band. SQL verifier uses the **same symmetric key**; this is NOT asymmetric public-key verification. Both key locations must remain inaccessible using the runtime SQL role or a client HTTP request. If this key-sharing topology is rejected by security review, **ADR must be revised before coding**; do not downgrade silently to free-form actor SQL parameters or a GUC.

**Out of scope:** a compromised trusted backend/signing service, key manager, DB owner/superuser, malicious migration, or attacker able to read the DB-held MAC key. A stolen SQL password alone (without leaked proof/key or control of the trusted signer) is the target attacker. SQL injection within the *same authorized connection/transaction* needs extra replay/payload tests; exact-signature target binding limits but does not magically eliminate all same-transaction attacks.

### 2.2 Canonical proof envelope v1 — format requirements for review

Use **one typed canonical encoder shared by signer and DB verifier** (or two independently implemented codecs with byte-for-byte test vectors). Reject all noncanonical input. Suggested `proof_payload_v1` field sequence, **all fields mandatory with distinct tags and fixed ordering**:

| Field | Binding |
| --- | --- |
| `domain`, `version`, `kid`, `deployment_id` | Exact ASCII domain `DXOS-WF-SQL-CAP`, version 1, selected key id and environment/cluster-bound deployment id (prevents cross-service/environment reuse). |
| `issuer`, `subject`, `actor_id` | Exact issuer and subject from verified OIDC claims; actor matches canonical `oidc:<base64url(UTF8(issuer))>.<base64url(UTF8(subject))>`; no normalization/case folding. |
| `required_authority` and `port_action` | Exact verified authority and one of SIX enum names `LOAD_DEFINITION/LOAD_INSTANCE/LOAD_HISTORY/CREATE_INSTANCE/COMMIT_ACTIVATION/COMMIT_TRANSITION`. Also encode high-level Gateway permission CREATE/ACTIVATE/TRANSITION/READ; an ACTIVATE-scope internal LOAD_INSTANCE is **not** a public READ grant. |
| `instance_id`, `resource_type`, `resource_id`, `definition_id`, `definition_version` | Exact target/definition binding (CREATE additionally uses generated instance ID; existing instance resource/definition must match authoritative persisted values after lock). No wildcard, nullable alias or implicit last-version fallback. |
| `transition_id`, `verified_transition_actor`, `expected_runtime_version` | Exact transition parameters, or *typed ABSENT* for irrelevant operations. Verified actor cannot be overridden by HTTP/SQL. |
| `proposal_sha256` | Hash of **complete canonical method input** (all snapshots, time seconds+nanos, lifecycle/state, record/actor, expected/proposed versions, definition ID/version). The DB function computes this hash **itself from typed SQL arguments**, not from the user's supplied hash. Internal guarded read methods bind their exact own argument set. |
| `pg_backend_pid`, `pg_xact_id_xid8` | Actual physical JDBC connection's backend PID and `pg_current_xact_id()`-assigned 64-bit transaction ID **after transaction start**; the SQL verifier recomputes both within the same PostgreSQL transaction. No cross-transaction reuse. |
| `issued_at_ms`, `expires_at_ms`, `nonce` | Signed issued time, bounded short expiry, 128+ random nonce; strict upper age/window plus clock skew limit, re-check expiration after waiting for the guard and immediately before a write. Timeout/expired => fail closed, never continue on a stale capability. |

**Canonical framing:** four-byte unsigned big-endian count/field byte-length prefixes with fixed tagged field order, explicit type tags for string, int64, bytes, absent. `String` fields use strict UTF-8 from a Java `CharsetEncoder` with `CodingErrorAction.REPORT` for malformed/unpaired UTF-16 surrogates; reject NUL, invalid Unicode, oversized fields and ambiguous encodings. PostgreSQL UTF-8 side must encode the same bytes (`convert_to(text,'UTF8')` only where approved). Never use Java's default replacement encoder, JSON serialization order, concatenated strings, locale transforms or different Unicode normalization in SQL. Integers use two's-complement big-endian signed 64-bit; booleans/enums fixed tags; arrays have canonical lengths and deterministic lexicographic element order. Exact `Instant` represented as epoch seconds and nanos, never milliseconds-only or floating-point timestamps. Reject invalid, missing, repeated or reordered tags. Define maximum total proof/message bytes and provide versioned **cross-language test vectors before implementation**.

Signature `mac = HMAC-SHA256(K[kid], canonical_payload)`. Wire envelope contains canonical payload plus 32-byte MAC; recompute from supplied SQL typed parameters and transaction identities **inside** trusted SQL before any protected read/write. Independently check signer-selected `kid`/deployment id, expiry, actor, operation and target, then post-lock authoritative ACL. MAC matching should avoid a data-dependent timing side channel where practical; use an audited constant-time comparison strategy rather than assume ordinary PostgreSQL `BYTEA =` is constant-time. A caller-provided digest does **not** substitute for computing it from method arguments.

### 2.3 Transaction-level issuance and verification protocol

1. **One JDBC port invocation -> one transaction -> one proof.** Java obtains `CurrentPrincipal.requireVerified()` once per HTTP request but never copies proof from an earlier port method. Its private signer takes only the verified caller + immutable operation-scope; it does not expose a sign-any-actor method to controller, SQL clients, or arbitrary app plugins.
2. JDBC obtains a **checked** `dxos_wf_runtime` physical connection; `setAutoCommit(false)`, `READ COMMITTED`, lock-capable mode for reads, approved finite timeouts. Query `pg_backend_pid()` and `pg_current_xact_id()::text` on **this same connection** to bind proof. `pg_current_xact_id()` allocates a real XID even for reads; cost and pooling implications must be acceptance-tested. If transaction poolers can route this invocation to another backend between calls, **reject that configuration**: same physical JDBC transaction required throughout.
3. Java signs the versioned payload **after** learning connection's backend PID/XID and **before** passing canonical method input. The online DB role has no ability to obtain the HMAC key; Java key comes from a separate secrets path, **not** from JDBC URL/GUC/database password. Never log proof payload+MAC, key, JWT, raw actor IDs or SQL string values.
4. The vetted `SECURITY DEFINER` function validates syntax/limits/MAC, backend PID/XID and token-age window against its protected HMAC key. It must check candidate target/resource privately, lock **permanent tenant guard FOR SHARE**, **re-check** the proof's freshness and current tenant/membership/resource/grant/authority/CREATE binding **after** lock (all `READ COMMITTED`). For writes re-check exact signed proposal against current snapshot+definition, then update on the same connection. Every SQL entrypoint independently verifies the proof; never rely on a transaction variable `SET LOCAL actor`.
5. The Java port method owns COMMIT/ROLLBACK. Known rollback -> typed sanitized access/domain failure; attempted uncertain write COMMIT or failed write rollback -> `COMMIT_OUTCOME_UNKNOWN`, **no blind retry**. A token expiring due to lock wait rejects before mutation with confirmed rollback; never refresh a proof by silently re-running a possibly committed write.
6. PostgreSQL policy mutators use a **separate authenticated administration/provisioner trust model**, their own allowlisted functions and `FOR UPDATE` guard protocol; runtime-capability key **MUST NOT** authorize `wf_policy_*` or `wf_provision_*`. The source/origin of legitimate admin operations is a separate P0 ADR; possession of a separate DB password alone is not by itself proof an admin command is permitted by application policy.

### 2.4 Key ownership / privileges (candidate — cannot be deployed before review)

- Generate per-environment K with a cryptographically secure secret generator; store securely on trusted backend outside SQL credentials; store verifier's symmetric copy in an owner-only protected table or audited secret store used *only inside* definer verifier. Owner is dedicated `NOLOGIN` `dxos_wf_owner`; runtime/admin/provisioner must neither SELECT the secret nor inherit or `SET ROLE` to owner/migrator.
- Verify `pgcrypto` support/configuration on **disposable PostgreSQL 17**, install under controlled schema; definer function has fixed safe search_path `pg_catalog,pg_temp` and uses **schema-qualified** verifier, table and extension functions. Revoke direct table rights and helper/private `EXECUTE` from `PUBLIC` and online principals; grant exactly six allowed SQL entrypoints to runtime *after* they are reviewed. Default PUBLIC EXECUTE on functions must be revoked **in the same DDL transaction** as creation.
- Rotate keys with `kid` + active/retired state and a bounded verification overlap (no old key issuance); revoke compromised keys immediately, invalidate open proofs, terminate sessions if needed. Prove secret never appears in PostgreSQL errors, user-readable catalog, query log, trace, client-returned values or backups accessible to the runtime role. Review how DB secret backups and Java secret storage are handled.
- Secure transport is required: pgcrypto executes on server; the wire proof is not encrypted data. Require TLS and verify transport/certificate, limit internal proof observability; signed payload is not a privacy mechanism. Review extension-level privileges, DB owners and role membership. If symmetric-secret custody cannot meet threat model, **block rollout** rather than treat HMAC alone as success.

### 2.5 Replay and SQL-only attacker model

- **Different connection/transaction:** exact `pg_backend_pid + xid8` binding, deployment and expiry must reject captured proofs reused elsewhere. PostgreSQL `pg_current_xact_id()` assigns a top-level transaction ID; test savepoints/exception subtransactions, session pooler behavior and potential backend PID reuse. XID8 is installation-local; deployment-specific key and ID are required.
- **Same transaction:** a SQL-injection adversary who has captured an *already-valid proof in the current transaction* might replay the identical method. It must not enable a different target, action, actor, transition or changed payload. A second CREATE is blocked by global PK, a second ACTIVATE by full lifecycle/snapshot comparison, and second TRANSITION by expectedVersion/history unique constraint; zero-new-row protected READ repeats are bounded to the same authorized target. This **does not claim cryptographic one-time-use**. If a true single-use requirement is part of threat model, add a separately reviewed, transactionally enforced nonce-consumption ledger; `nonce` alone without storing used values is **not** replay prevention.
- **Runtime-password-only attacker:** with a fresh database transaction they can read their PID/XID, but cannot produce a valid HMAC without separate trusted Java/owner-only secret. Tests must show direct table SELECT/DML denied, forged actor/target/action/payload proof rejected, non-approved SQL helpers inaccessible and unauthorized policy mutations impossible.
- **Known limitations:** a compromised legitimate signer could mint fake principals; a runtime attacker who obtains a live proof for an authorized action may be able to reissue exactly that action within the same transaction until Core's state/version or optional nonce enforcement rejects repetition. This is not a guarantee of absolute protection from arbitrary SQL execution; the scope is narrowly defined.

## 3. Consequences for six-port-method map and ADR-0023

- **CREATE public Gateway:** use **C3 only**. Replace the `CREATE loadInstance(generatedId)` row in [six-method matrix `5](../contracts/issue-23-workflow-port-sql-authorization-matrix-v1.md) with **NO PRELIMINARY INSTANCE QUERY**; `loadDefinition` under restricted CREATE scope -> `WorkflowInstance.notStarted` -> guarded `createInstance`. `loadInstance` remains an authoritative full-snapshot port method for **authorized READ/ACTIVATE/TRANSITION** only. Existing direct `WorkflowRuntime.createInstance` semantics are untouched and **must not** be exposed over secured HTTP. Direct production bean/controller routes calling unguarded Core runtime remain prohibited.
- **Every SQL port method:** proof binds exact SQL function name and required Gateway authority, target, per-method payload hash and actual transaction identity. For internal `loadDefinition` or `loadInstance` under ACTIVATE/TRANSITION, their proof names **that port method** but grants only the corresponding operation-scoped internal read, not public READ. Never reuse a previous port transaction's proof.
- **Writes:** ADR-0023 Option A remains: current `WorkflowPersistencePort` write methods return only after **confirmed durable COMMIT**, retaining same physical checked connection and tenant `FOR SHARE` lock from post-lock ACL check through state/history write and COMMIT.
- **Admin operations:** NOT covered by this runtime proof; must define separate authenticating provenance/guard semantics before turning on ACL mutation APIs. No actor GUC, unsigned Boolean, or blanket owner grant.
- **Ambiguous response:** service must not auto retry `COMMIT_OUTCOME_UNKNOWN`; DEFINE reconciliation/idempotency separately. A generated-ID collision with confirmed no-commit is sanitized; no hidden 404/409 with revealing instance identifier.

## 4. Acceptance checklist and independent sign-off

**C3 / CREATE:**
- Forced collision with a hidden/existing instance in another tenant returns sanitized failure and never executes protected `loadInstance` on colliding ID.
- Missing/forbidden exact definition binding, invalid definition, generated ID timestamp/initial-state parity, race collisions and SQL conflict handling; no client-owned `instanceId`.
- No unguarded Core Runtime bean/controller/API path is exposed. Review the limited CREATE sequencing difference (definition-first vs Runtime probe-first) as a Gateway-specific behavior.

**HMAC / SQL capability:**
- Golden cross-language Java/PG17 byte-for-byte encoding + HMAC vectors for ASCII, non-BMP Unicode, combining forms, exact issuer/subject, NUL/replacement rejection, signed negative int64 and nanos, maximum sizes and method payload field coverage.
- Prove `pgcrypto` extension available, protected key accessible only in vetted definer, no direct secret/privilege/default-PUBLIC bypass, forged SQL proof/actor/authority/operation/target/version/payload denied. Verify timing comparisons or document mitigations accepted by reviewer.
- Same-transaction proof works with a physical JDBC connection; different connection/transaction/restarted session replay fails; forced expiry across `FOR SHARE` lock wait fails closed; savepoint rollback lock revalidation; strict no fallback if verifier unavailable.
- Multiple valid scoped methods in one HTTP request each get a fresh transaction proof; no reuse or target/action confusion. Admin/provisioner cannot exploit runtime function roles.
- PostgreSQL effective role tests with actual runtime-only credentials and two-connection revoke-first/write-first/read/history races; unknown COMMIT, rollback failure, no automatic retry; JWT/JWKS 401/403/hidden-404 and Request regressions later.
- Require written independent PostgreSQL **and cryptography/security** review of actual verifier, key custody and SQL function signatures, together with V5 FK/collation/roles/manifest rollout; **no executable migration or production HTTP before PASS**.

**Design disposition:** C3 accepted as the *preferred gateway CREATE strategy*, HMAC-SHA-256 v1 as a *specific proposed strong SQL-authentication protocol*; **both conditional on the above sign-offs**. ADR-0023 Option A remains in effect. This document removes ambiguity over the engineering choice but does **not** establish actual SQL-code safety or approval for implementation.
