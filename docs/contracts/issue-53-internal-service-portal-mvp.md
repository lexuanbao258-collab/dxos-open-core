## 2. Shared rules and ownership

The Portal is an independent HTTP consumer. For **CREATE**, the future Backend Application must: (1) verify OIDC issuer/subject; (2) classify visibility and tenant membership from authoritative resource context without disclosing it; return indistinguishable HIDDEN/404 before any protected materialization; (3) require explicit CREATE grant **and** the exact verified `workflow:create` authority; (4) only then check the exact active definition/resource binding and load the authoritative immutable definition; (5) perform a final post-guard ACL check inside the write transaction before commit. Do not preload, cache or query the definition or private binding before authorization. If a new resource cannot be classified without a side-effecting write, CREATE remains **BLOCKED** until a safe preauthorization design is reviewed. The present #23 Phase 1 policy seam expects a definition object and does not itself prove this complete ordering or transactional guard.

Workflow alone supplies current state, lifecycle, runtime version and successful transition history. Business facts must not independently assert a contradictory `status`; a read model can join them after resource-scoped authorization. Activation is separate and keeps version **0**. Each successful transition increments version once; `expectedVersion` is the snapshot version submitted, never a client-selected target state. Definition changes require a new version; running instances remain pinned. **Instance ID ownership is OPEN:** #22 foundation accepts caller-provided `instanceId`, while #22 Phase 2 proposes server-generated opaque IDs to avoid probing; no production contract is ratified. There is no generic reopen, timer, SLA, guard script, notification or attachment transaction in Core.

Business roles below are **eligibility predicates**, not JWT authorities. For **READ/HISTORY, ACTIVATE and TRANSITION**, verify identity, classify authoritative instance/resource visibility before disclosure, then require the operation's own exact authority (`workflow:read`, `workflow:activate`, `workflow:transition` respectively), explicit resource/action ACL and applicable business predicate. Internal authorization lookup may use only the minimum authoritative reference needed to classify visibility; it must not expose snapshots, history, existence or private binding to the caller or materialize a definition before authorization. Use the persisted binding for these operations after access is granted. Do **not** impose CREATE binding checks or an unrelated READ grant on ACTIVATE/TRANSITION. Writes need their final ACL check in the write transaction; prechecks alone do not settle revoke races. Canonical actor is derived server-side from verified issuer and subject; client body/header/display name never supplies actor, requester or ACL. The **original requester** is an Application business fact, distinct from ACL resource owner. Neither requester nor owner bypasses explicit ACL or exact JWT authority. Assignee, processor and confirmer are checked against authoritative business facts and verified principal; assignment targets an eligible tenant member. A changed assignee or revoked grant invalidates subsequent action. List/detail/history must filter at the backend before returning protected data. A visible resource without permission is 403; hidden, cross-tenant or nonexistent resources have indistinguishable 404 status/body; missing/invalid/expired authentication is 401 before protected lookup; unavailable authorization fails closed with sanitized non-success (current Gateway bridge candidate: 503). UI button visibility is advisory only.

## 3. UC-A — IT Helpdesk software incident (candidate live definition)

**Actors:** requester (employee), IT triager, assigned IT processor, confirmer, close operator. Requester confirmation is approved for the **mock only**; close operator and live eligibility await decision. **Preconditions:** verified session; authoritative visibility/membership classification, explicit create grant and exact verified authority; valid request title, description and approved IT type; exact definition binding checked only after authorization. No inventory, RAM purchase or budget approval.

**Main flow:** requester submits facts → after the ordered CREATE gate, Application creates the business resource, Workflow instance and activates it → IT triager accepts/classifies → a separate, authorized Application assignment becomes effective (API/consistency **OPEN**) → assigned IT processor starts work and records a nonblank resolution → requester views result and confirms → authorized close operator closes if a live terminal step is approved. State path proposed for live definition: `SUBMITTED → TRIAGED → IN_PROGRESS → RESOLVED → CONFIRMED → CLOSED`. `CONFIRMED` is deliberately distinct from `CLOSED`; for the ratified Portal mock, `CONFIRMED` is the demonstration stop and there is **no** close action. **Postcondition:** each confirmed transition has one ordered Workflow history record and a matching version; Application holds the associated facts. Only `CLOSED` is terminal in the candidate live graph.

**Alternative/exception flows:** missing information is validation failure before transition, with no new state; out-of-scope rejection and requester dispute/rework require separately reviewed edges and policy, so they are **OUT OF SCOPE** for this MVP path and safely rejected as undeclared transitions. A caller other than the original requester cannot use the candidate requester-confirm action; even the original requester still needs explicit ACL and exact authority. Lost response, duplicate click, changed assignee, failed upload and concurrent versions follow section 8; none may create a second silent transition. Notification is not required for state change.

## 4. UC-B — Facility Maintenance incident (candidate live definition)

**Actors:** requester (employee), facility coordinator, assigned technician, acceptance actor. Exact acceptance actor (requester or designated inspector) remains **OPEN**; whether a distinct close operator/action is needed is also **OPEN**. **Preconditions:** verified session, authoritative visibility/membership classification, explicit create grant and exact verified authority; nonblank title, problem description and location validated from input before any side-effecting persistence; eligible assignment target. A photo is optional and cannot gate the base path until protected attachment API exists.

**Main flow (candidate):** requester reports issue → coordinator accepts and assigns a technician → technician starts and records repair outcome → eligible acceptance actor inspects and accepts, with that **single candidate action** reaching `CLOSED`. Candidate path: `SUBMITTED → ACCEPTED → ASSIGNED → IN_REPAIR → AWAITING_ACCEPTANCE → CLOSED`. The acceptance actor and authority still need review; this does not approve a separate close operator. If acceptance and close must be two actions, the team must first decide the actor, state and transition; none is added here. **Postcondition:** Workflow state/history is authoritative; assignee, location, repair notes and acceptance facts belong to Application; no direct state setter is exposed.

**Alternative/exception flows:** out-of-scope rejection needs reason and a reviewed terminal edge; failed acceptance could return to `IN_REPAIR` only if a later immutable definition version explicitly declares the cycle, otherwise reject the action; lost assignee rights blocks the next write. These branches are **OUT OF SCOPE / SAFE-REJECTED** in the current candidate path. Upload failure leaves no false attachment reference or accepted transition.

## 7. Transaction and consistency decision for review

**Existing guarantee:** Workflow persistence port owns an authoritative, confirmed durable state/history write per operation; successful return follows COMMIT (ADR-0023). The Request prototype's JPA transaction covers only its Request row/history, not Application+Generic Workflow. **Proposal, not implementation:** Application orchestration would own coordination of business facts with Workflow and any separate Application transaction/reconciliation. No shared transaction, operation receipt, idempotency API or cross-PostgreSQL/object-storage atomicity exists in Generic Core. Do not wrap the Workflow port in an outer transaction that returns before its confirmed COMMIT.

For a future LIVE command, validate input without side effects, complete verified identity and operation-specific visibility/authority/resource ACL **before any business-fact or pending-intent write**, then recheck the authoritative ACL at the final write guard inside the relevant transaction. A possible Application design records pending facts after that gate, invokes one Workflow write and marks facts effective only after confirmed Workflow COMMIT; this design and its transaction boundary remain **OPEN / BLOCKED**. Any pending facts must stay separate from authoritative Workflow state; known rejection discards or marks them without claiming a transition. If an ACL or assignment is revoked between checks, the final guard must prevent the unauthorized write. No security meaning attaches to a client-supplied operation identifier.

For `COMMIT_OUTCOME_UNKNOWN` or a lost response, retain the exact attempted proposal and use **authorized** `loadInstance`/`loadHistory` evidence already provided by the port: for create compare the full initial snapshot, definition binding and resource (an identical instance does not prove which writer created it); for activation compare the full snapshot/lifecycle, since version remains zero and later transitions may advance it; for transition compare the exact proposed record at its resulting version and subsequent authoritative history/snapshot. Separate reads may straddle concurrent changes and must be repeated when needed. A missing/old snapshot or ambiguous matching data does not prove rollback or ownership of the write. If the outcome cannot be established, keep it **UNKNOWN**, use adapter/operator reconciliation, and neither retry blindly nor report success. An explicit new attempt requires a settled prior outcome and fresh authorization/concurrency decision. Attachment upload, if later approved, needs separate provisional-object cleanup and must not claim atomicity with PostgreSQL. The Application persistence/recovery design must be reviewed before LIVE use; it does not require a new Core port or unrelated business feature.

## 8. Failure classification and acceptance tests

`SUPPORTED` means the named invariant exists in Core/prototype tests or the mock decision; it does **not** imply secured live E2E. `SAFE-REJECTED` is the required behavior at the future boundary and remains unverified live until its test passes. `OUT OF SCOPE` means no transition/API is promised.

| Case | Required result / acceptance assertion | Current classification |
| --- | --- | --- |
| Create/activate each definition | Correct immutable binding, `NOT_STARTED → ACTIVE` v0, no history on activation; two definitions run on unchanged Core | **SUPPORTED Core contract; BLOCKED live E2E** |
| Valid IT/Facility transition | Exact key/source/actor/facts; target from definition; one version increment and one ordered history record; business facts match after confirmation | **SUPPORTED Core invariant; BLOCKED application integration** |
| Missing/invalid/expired token | 401 before protected lookup/write; forged body/header actor never trusted | **SAFE-REJECTED target; BLOCKED real filter-chain proof** |
| Visible but forbidden; hidden/nonexistent/cross-tenant IDOR | 403 for visible denial; indistinguishable 404 for hidden/missing; no protected data, history or write | **SAFE-REJECTED target; BLOCKED ACL proof** |
| Invalid key/source, early close, wrong actor, rejection/rework edge absent | No state/history/fact write; normalized invalid/forbidden response; no invented branch | **SUPPORTED Core invalid-transition invariant; SAFE-REJECTED at HTTP** |
| Stale `expectedVersion`, two writers, double-click | At most one confirmed transition; 409 conflict; reload authorized snapshot before any explicit new attempt | **SUPPORTED Core/port invariant; BLOCKED real HTTP/race proof** |
| Revoked membership/assignee during action | Final authoritative ACL/assignment check at write boundary; no unauthorized materialization or commit | **SAFE-REJECTED target; BLOCKED #23 race proof** |
| Upload failure | No false attachment reference or state transition that requires it; cleanup/reconcile provisional object | **OUT OF SCOPE until protected API** |
| Lost response / `COMMIT_OUTCOME_UNKNOWN` | Compare exact attempted snapshot/transition record with authorized instance/history; if ambiguous keep UNKNOWN; never automatic write retry or false success | **SUPPORTED port semantics; BLOCKED application recovery** |
| Mock IT processor completes / requester confirms | `RESOLVED` remains nonterminal; original-requester-only mock `confirm` reaches `CONFIRMED`, two timeline events; no implicit `CLOSED` | **APPROVED MOCK UX only**; operator-reported local at PR #51 HEAD `076b9cb`: 31/31 unit/component PASS, 14/14 Playwright smoke PASS, build and security scan PASS; not independent CI or Portal LIVE |
