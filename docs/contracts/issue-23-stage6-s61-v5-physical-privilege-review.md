## DB1: Five-table physical model (proposed, not migrated)

Use the existing private Workflow Flyway schema (not public), subject to schema-guard/manifest and PostgreSQL 17 collation compatibility.

| Table | PK / core fields | Required FK, CHECK, UNIQUE and immutability |
|---|---|---|
| tenant_guards | tenant_id TEXT PK, acl_revision BIGINT default 0 | Nonblank tenant; nonnegative monotonic revision. Permanent row: never DELETE, reinsert, reuse or move tenant ID. Every authorized read/write holds FOR SHARE, every membership/ACL/owner/binding/tombstone mutator locks same guard FOR UPDATE. |
| tenant_memberships | (tenant_id,actor_id) PK, active BOOLEAN NOT NULL | tenant_id FK to tenant_guards ON UPDATE/DELETE RESTRICT; actor_id exact canonical OIDC identity, nonblank; identity columns immutable. Proposed deactivate sets all positive grants false in the same transaction; reactivate never restores them. |
| resource_registry | (resource_type,resource_id) **global** PK; tenant_id,owner_actor_id,lifecycle,created_at,tombstoned_at | Tenant FK RESTRICT; UNIQUE(tenant_id,resource_type,resource_id) for ACL FK; proposed composite owner membership FK (tenant_id,owner_actor_id) RESTRICT. Nonblank IDs/owner; ACTIVE iff tombstoned_at null, TOMBSTONED iff timestamp present. Tenant/key/created_at immutable; no delete/re-register/resurrection. ACTIVE owner must be active in that tenant (DB2a). Owner is not an operation grant. |
| resource_acl | (tenant_id,resource_type,resource_id,actor_id,operation) PK; granted BOOLEAN NOT NULL | Composite FK to registry and membership (tenant_id,actor_id); only the four exact values workflow:create, workflow:activate, workflow:transition, workflow:read. Positive grant never overrides inactive membership/tombstone or missing JWT operation authority. |
| workflow_definition_bindings | (tenant_id,resource_type,definition_id,definition_version) PK; active BOOLEAN NOT NULL | Tenant FK + exact (definition_id,definition_version) FK to V3 workflow_definitions, RESTRICT. Nonblank resource/definition IDs; nonnegative version. Exact active binding mandatory only for new CREATE; cannot alias or silently pick latest version. |

**Constraints requiring independent physical sign-off:** CHECK/FK alone cannot prevent deleting/recreating guard, resource key/tenant UPDATE, resource tombstone reversal or SQL-based ACL bypass. Design reviewed immutability triggers AND role-restricted narrow mutation functions. Determine FK collation/operator-class behavior against existing V3 definitions before selecting COLLATE "C"; check Unicode identity equality, indexes, and V1–V4 pinned manifests. Do not change V1–V4. Proposed indexes only after EXPLAIN/representative disposable PG17 benchmark.

### DB1a: Immutable identity enforcement layers — DEC-D2-02

No tenant ID or resource `(resource_type,resource_id)` can be renamed, moved to another tenant, deleted/reused, or recovered from a tombstone. Owner reassignment changes metadata within the same tenant only. Required layers for the future reviewed design:

| Layer | Proposed enforcement / review obligation |
|---|---|
| Constraints | NOT NULL/nonblank exact keys; permanent guard PK; global resource PK; tenant/resource composite UNIQUE; ACL FKs bind both resource and membership to the **same tenant**; owner membership FK; exact definition/version FK. Identity FKs use ON UPDATE/DELETE RESTRICT, no cascades. CHECK constrains lifecycle and tombstoned timestamp consistency, nonnegative revision/version and four exact operations. |
| Triggers | Reject UPDATE of guard tenant ID, registry tenant/resource keys or created_at; reject tenant/resource DELETE and TOMBSTONED → ACTIVE; preserve the original tombstoned_at on all later writes. Reject membership/ACL/binding identity-key rewrites; changes use explicit deactivate/revoke/new-key decisions. Cross-row active-owner/positive-grant checks require guarded functions plus reviewed triggers, not a CHECK that queries another table. Guard revision cannot decrease/reset; no no-op UPSERT may remap identity. |
| Privileges | Online runtime/admin/provisioner have no direct table DML, TRUNCATE, ownership, ALTER/trigger disable, replication-mode bypass or SET ROLE to owner/migrator. Reject effective inherited/default/PUBLIC bypasses, not just explicit grants. Audit identity protections against both narrow API misuse and offline-owner trigger tests in disposable PG17; owner/superuser/malicious migration remains outside the runtime-password threat model. |
| Mutation protocol | Authenticate/bind action+tenant+exact resource; guard FOR UPDATE before children/FKs; re-read immutable identity/lifecycle; allow only enumerated field changes; revision + append-only audit + durable COMMIT atomically. Tombstone is one-way; stale ACTIVE input, conflict UPSERT, delete/reinsert and restore/import cannot reset it. Any conflict rolls back without repairing/rebinding the key. |

Guard creation is the sole bootstrap exception: a separately reviewed provisioner transaction establishes a never-used tenant ID with a unique INSERT and creation audit before any child; a concurrent duplicate fails without replacing/resetting the guard. Subsequent operations use that permanent row; no delete/recreate shortcut. V1–V4 stay byte/checksum immutable; any future additive enforcement on existing V3 objects needs separate compatibility/manifest approval.

**Tenant-disable: proposed DEFER from MVP v1.** No physical tenant lifecycle, disable flag, lifecycle column, disable API or associated authorization semantics has been approved. A permanent guard reserves identity; it does not encode an active/disabled tenant state. Reopen only if a demonstrated business requirement is reviewed, with explicit owner/product, lifecycle, authorization/concurrency and physical-design decisions before implementation. Do not invent a column or alter the five-relation schema to fill this gap. Membership deactivation and resource tombstones remain separate proposals/invariants and do not establish tenant-disable behavior.

### DB1b: New registration versus legacy reconciliation — DEC-D2-01

**Source limitation:** V3 instances have global instance IDs and resource keys, no tenant ID and no registry FK. A wrong registry association could therefore expose *all* old instances for that key to the wrong tenant. A global PK, ACL FK or V3 history actor cannot prove historical tenant ownership. V1/V2 Request assignee and V4 example definitions supply no authoritative tenant mapping.

**Separate controlled provisioning allowlists; no arbitrary online registration in MVP v1:** NEW registration is a manifest-approved provisioning operation, not an open application/API path for callers to register arbitrary resources. It accepts only a never-used global key with **no matching V3 instance**; reject if a legacy row, registry row or tombstone exists. It cannot silently adopt legacy rows through INSERT/UPSERT. LEGACY reconciliation is an offline, separately authorized provisioning operation requiring its own reviewed manifest; not a flag enabling NEW registration to bypass checks. Registry and V3 absence checks must be serialized against every writer, including insertion of an initially absent key.

Both provisioning routes require reviewed authoritative tenant/resource/owner evidence bound to the approved manifest and authenticated action: NEW registration declares an empty legacy inventory, LEGACY reconciliation declares the complete reviewed set. A NEW manifest cannot authorize legacy adoption; neither route accepts a caller-chosen tenant/owner as sufficient evidence. Provisioner credentials alone do not approve the mapping.

**Authoritative source still unproven:** this design does not establish an existing trusted tenant/resource/owner system of record. Before either route is approved, identify that source, its accountable owner, provenance, access controls and independent mapping-validation evidence. Manifest approval or a digest cannot make an unsupported assertion authoritative. If the source cannot be demonstrated, both NEW and LEGACY provisioning stay blocked; no fallback to HTTP payload, token tenant, Request assignee or Workflow history actor.

**Required manifest and approval:** version/digest, environment/schema and pinned V1–V4 compatibility baseline; authoritative external resource evidence and accountable reviewer/owner approval; exact resource key → tenant + canonical owner; owner membership evidence; complete set of matching V3 instance IDs with exact persisted resource/definition/version and inventory fingerprint; intended disposition (reconcile or quarantine), expected registry absence/state and tenant revision. Inventory fingerprint must detect added/deleted/rebound instances and snapshot/history drift between inventory and application. Bind any membership/binding/grant provisioning to separately reviewed explicit decisions; the mapping alone creates no positive ACL grant. Manifest artifacts contain sensitive inventory and remain operator-only. A digest proves artifact integrity, **not correctness of the asserted tenant**; conflicting/missing business evidence blocks reconciliation.

**Proposed controlled protocol, only after approval:**

1. Establish global resource-key uniqueness across consumers and inventory all V3 instances for each candidate key. If the same key represents different tenants/resources, quarantine the **whole key**; never choose one tenant or reconcile only convenient instances. Missing/ambiguous/unapproved mapping remains HIDDEN, with no ordinary Workflow access.
2. Fence and drain **all legacy V3 writers** before capturing the final inventory/approving its manifest; include old pools, jobs, offline provisioning and in-flight transactions. Current PostgresWorkflowPersistence ignores V5 guards, so a tenant lock or READ COMMITTED absence query alone is insufficient. The reviewed future cutover must prove effective privilege fencing and no unguarded writer; if it cannot, STOP. No fence or database change is executed in S6.1.
3. While the fence remains effective, authenticated reconciliation takes permanent guard FOR UPDATE before children, verifies environment/manifest approval/digest, exact fresh inventory, expected revision/registry state, active owner membership and whole-key coverage. Tenant/resource/definition conflicts, drift, a tombstone or stale revision abort the transaction for new inventory and review; never patch the manifest automatically or use ON CONFLICT to reassign a tenant.
4. Insert only the reviewed registry association and separately approved policy facts; record manifest digest, provenance, affected identities and resulting revision in durable audit on the same transaction. Do not rewrite V3 resource references, IDs, definition pins, snapshots, history or timestamps. Confirm COMMIT, then validate counts/key sets, restrictive FK compatibility and no unintended visibility from a fresh privileged verification connection. A partial run cannot make an unapproved key visible; retries require proving prior outcome, never replay an uncertain commit.
5. Keep old-writer fencing through a **coordinated deployment**, not merely until registry INSERT commits: verify drained writers and effective privileges; deploy the reviewed guarded adapter while affected traffic remains held; apply reviewed privilege changes in their own DB transaction(s); then verify effective runtime/admin/provisioner permissions and guarded behavior as actual login roles. Application deployment and DB privilege changes are **not one atomic transaction**. From a fresh verification connection, check inventory, policy/audit state, no unintended visibility and rejection of old-writer credentials/pools before allowing guarded traffic. Only guarded CREATE on approved resources and manifest-approved provisioning may write; arbitrary online registration stays closed. Validate NEW's no-legacy precondition under the same fence/serialization. Drift, failed checks or role incompatibility keep the fence and deployment blocked; no premature REVOKE that breaks the current backend.

**Rollback/recovery gate:** review and rehearse failure after each deployment/privilege step. Keep affected traffic stopped and legacy writers fenced while recovering; rollback of application deployment must not restore old direct-table privileges, old pools or unguarded traffic. Reconcile confirmed committed DB/policy/audit state, restore a reviewed compatible guarded application/privilege configuration, and repeat effective-role and fresh-connection post-checks before resuming. If no compatible safe rollback exists, retain the fence and use reviewed forward recovery. Unknown COMMIT requires explicit reconciliation, never blind replay. These are coordinated operational steps, not a distributed or cross-application/DB atomic commit; no step runs in S6.1.

The fence, manifest source/approval process, integrity storage and exact inventory/future FK validation mechanism require independent DB review. No reconciliation, auto-backfill or database access is authorized by this design.

## DB2: Mandatory trusted policy mutation APIs

Only enumerated, separately authenticated policy-admin/provisioner SQL APIs may create tenants, register/tombstone resources, grant/revoke membership/ACL, change owner within same tenant, activate/deactivate exact definition binding, and provision immutable definitions. Every such API MUST:
1. Begin a checked physical READ COMMITTED JDBC transaction and lock the permanent tenant guard row FOR UPDATE **before** any protected dependent row or FK lock.
2. Recheck admin/provisioner authorization and immutable target; mutate only its bound tenant; increment acl_revision and write audit record on same transaction.
3. COMMIT or confirmed ROLLBACK while holding the guard; no savepoint rollback releasing guard then continuing without reacquisition and a full policy recheck.
4. Reject cross-tenant transfer, key reuse, tombstone resurrection and unreviewed generic SQL executor. Apply the proposed DB2a membership/owner lifecycle without restoring stale grants. Multi-tenant mutations excluded from MVP unless deterministic sorted-guard locking is reviewed. Tenant bootstrap follows DB1a; legacy reconciliation additionally requires DB1b's writer fence.

Guard/row lock order for all operations and admin jobs: tenant guard -> resource -> instance -> history, including FK and trigger locks.

### DB2a: Membership revocation, ownership and durable audit — DEC-D2-03

**Proposed lifecycle, PENDING OWNER / YẾN / PostgreSQL REVIEW:**

- **Deactivate:** under the exact tenant guard FOR UPDATE, recheck admin proof, target membership and revision; enumerate every resource/grant for that actor in the tenant. Change every positive resource ACL row to `granted=false`, resolve ACTIVE-resource owners, and set membership inactive in **one transaction** with revision and audit. Retain revoked rows; no soft mask leaving `granted=true` to revive later. Grant APIs reject inactive membership and serialize on the same guard, including batches. Any missing audit/owner resolution or other failure rolls back **all** changes.
- **Reactivate:** set membership active under the same protocol, leaving all revoked grants false. No historical grants, bindings, role changes or ownership-derived operation permissions are automatically restored. Each regrant is a new explicitly authorized, audited action against an ACTIVE resource and active membership. Reactivation alone does not undo the prior owner reassignment.
- **Owner reassignment:** every ACTIVE resource must have an active member of its immutable tenant as owner. Before deactivating an owner, atomically reassign **all** affected ACTIVE resources to explicitly selected active same-tenant members, otherwise reject the entire deactivation. No fallback to the operator, JWT tenant or cross-tenant owner; no implicit ACL grants or grant copying to the new owner. Tombstoned resources may retain inactive owner provenance and cannot be restored. A same-tenant membership FK alone cannot enforce the owner's active flag; guarded owner-change/deactivation APIs and cross-row trigger checks must preserve this invariant under concurrent operations.
- **Durable audit:** append actor/admin authentication provenance (no secrets), action, exact tenant/resource/member identities, old/new membership/grant/owner values, reason/approval reference, manifest digest if applicable, correlation/idempotency reference and previous/resulting revision + timestamp. Enumerate affected grants/owners; aggregate counts alone are insufficient. Record audit and mutation on the same physical transaction; audit write failure aborts it. Only vetted functions append; online roles cannot update/delete/truncate audit or bypass it. Retain audit across revoke/reactivate, tombstone and retries; an idempotent no-op must not resurrect grants or fabricate a second state change. Known rollback commits neither mutation nor success audit; uncertain COMMIT uses explicit reconciliation, no blind retry.

The five relations are **business ACL relations**, not a claim that durable audit storage already exists. V3 Workflow transition history is domain history and cannot serve as membership/provisioning audit; application logs are not an atomic durable sink. Exact append-only audit relation/outbox, retention/access privileges and restoration controls remain D2/D3 design blockers for separate review; do not add a table or migration here. See [PG17 matrix](../verification/issue-23-stage6-pg17-acceptance-matrix.md) for revoke/reactivate, owner, audit-failure and concurrency acceptance cases.

**CREATE classification:** use the comparison and exact truth table in [contract §10/§12](issue-23-stage6-s61-postgres-acl-transaction-contract.md), **DEC-D2-04 OPTION 2 SEMANTICS AGREED BY YẾN; ORCHESTRATION/DATA-ACCESS CONTRACT REVIEW OPEN** ([Yến's review](https://github.com/lexuanbao258-collab/dxos-open-core/pull/50#issuecomment-6289261865), [Stage 6.1 §13](issue-23-stage6-s61-postgres-acl-transaction-contract.md#13-dec-d2-04-option-2-bindingdefinition-non-materialization-contract-2026-10-20)) ([Issue #23 owner record](https://github.com/lexuanbao258-collab/dxos-open-core/issues/23#issuecomment-6288471117)). Identity → reliable source → visibility → explicit CREATE grant + exact JWT authority → exact active binding is NOT current Stage 5 sequencing and must not be represented as implemented. Only a visible, CREATE-authorized caller may trigger exact definition/binding materialization. **A source-backed early ACL snapshot MUST NOT preload, materialize or populate bindings (including from a cache); current Stage-5 ResourceAclSnapshot contains an eager activeDefinitionBindings set and is NOT proof of this property.** The future guarded reader must obtain only minimal ACL facts for classification, with exact binding and definition access gated until both grant and JWT authority pass; no change to the six Workflow Core persistence port signatures. D4 must review how authority-denial classification coexists with capability validation; no SQL/JWT proof shortcut.

## SQL-A: Effective role/privilege matrix (proposed)

| SQL role | V3/V5 direct protected tables | Schema/DDL/role escalation | Permitted functions | Signer/verifier material |
|---|---|---|---|---|
| dxos_wf_owner (NOLOGIN) | Owner internally | Owner only, never an online login | Owns audited definer/private helpers | DB verification key custody only under reviewed owner/private mechanism |
| dxos_wf_migrator (offline) | Controlled deployment | Approved additive migration only; never in HTTP pool | Controlled install only | No request signer |
| dxos_wf_runtime (LOGIN) | **NO** protected SELECT/INSERT/UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER/MAINTAIN | **NO** schema CREATE, ALTER, DISABLE TRIGGER, superuser/BYPASSRLS, owner inheritance or SET ROLE | EXECUTE only the **six** reviewed wf_port_* exact signatures | **NO** key, private helper, signer secret |
| dxos_wf_policy_admin | **NO** direct table DML/SELECT | **NO** owner/migrator escalation | EXECUTE only audited wf_policy_* with guard/mutation proof | Dedicated admin authentication |
| dxos_wf_provisioner | **NO** direct protected DML/SELECT | **NO** owner/migrator escalation | EXECUTE only audited wf_provision_* | Dedicated provisioner authentication |
| PUBLIC, Supabase API roles, unrelated Request roles | **NO** | **NO** | **NO** Workflow protected EXECUTE | **NO** |

SQL audit MUST verify effective permissions including inherited role membership, role SET privilege, default PUBLIC function EXECUTE, schema USAGE/CREATE, all current V3 and planned V5 tables, exact overloaded function signatures, pg_auth_members, pg_proc, pg_default_acl and test negative SQL as actual runtime login. ALTER/TRIGGER disable derive from ownership, not simply a table GRANT.

SECURITY DEFINER functions must be owned by a non-login role; pin search_path to pg_catalog,pg_temp; fully qualify protected references; ban untrusted dynamic SQL; REVOKE PUBLIC EXECUTE **in the creation transaction**, then GRANT narrow EXECUTE per signature. Review globally set function creator default privileges and existing grants. Current PostgresWorkflowPersistence uses direct V3 SQL: REVOKE/switchover before the guarded adapter is ready would break the backend. Do not perform it.

## SQL-B: Caller proof design (P0 — NOT approved)

Keep ADR-0024's conditional **HMAC-SHA-256** candidate for the explicit stronger threat: stolen runtime SQL credentials alone must not forge another principal or read/mutate protected rows. An actor string, boolean, arbitrary JWT parameter or GUC is not DB-verifiable. The proof is created by a trusted signer only *after* CurrentPrincipal.requireVerified(), with key custody separate from runtime DB password.

Exact proposed typed binary envelope includes domain/version/kid/deployment id; strict UTF-8 verified issuer+subject and canonical oidc identity, exact authority + high-level operation + one of six port actions, bound instance/resource/exact definition/transition and full canonical proposal digest, the **actual same JDBC backend PID and transaction XID**, issuance/expiration and >=128-bit nonce. Bind/verify typed absence explicitly. One checked physical transaction per port method has a new proof; a preliminary read proof is never reused by a final write. SQL must derive actor/target/proposal binding independently from typed inputs, check MAC/replay/expiry/transaction identity before protected materialization and recheck expiry/current ACL after taking guard.

**Independent P0 review required:** precise versioned length-prefixed field encoding/order and strict malformed UTF-16 rejection, cross-language Java/PostgreSQL non-ASCII test vectors, signer and DB-held secret isolation, key rotation/revocation, timing-aware MAC check, expiry under lock waits, replay/nonce policy, transaction pooler backend affinity, key/actor logging audit and negative SQL tests using ONLY stolen-runtime-role capabilities. Previous PR #36 HMAC and V3 parity fixtures are separate, test-only demonstrations; do not claim combined protection. The explicitly **PROPOSED / NOT ACCEPTED** [ADR-0025 trusted-backend threat model](../adr/ADR-0025-proposed-mvp-trusted-backend-threat-model.md) evaluates deferring HMAC from the demo while disclosing that stolen online runtime DB credentials might spoof actors via allowed SQL functions. Narrow grants alone do not prove actor origin; until owner/security approval and formal ADR-0024 supersession, D4 HMAC gate remains BLOCKED.

## SQL-A simplification acceptance — proposed, not reduced privileges

The MVP does NOT require a fixed count of 16 privileged SQL helpers. Inventory the six exact Workflow persistence ports and each necessary membership, resource ownership, grant/revoke, definition binding, provisioning and append-only audit mutation. Merge or eliminate redundant admin/provisioner entrypoints **only if** every exposed entrypoint has one reviewable, bounded purpose, enforced owner/admin proof as required by the selected threat model, consistent tenant guard locking, protected audit and fail-closed negative tests. Do not equate fewer helpers with fewer security requirements.

**Minimum invariant:** runtime LOGIN retains no direct V3/V5 SELECT/DML or role/DDL escalation; only reviewed exact-signature port EXECUTE. No PUBLIC/default EXECUTE or arbitrary SQL. Policy-admin/provisioner must not become an unrestricted backdoor. SQL privilege sign-off remains **D3 BLOCKED**, and V3 direct-SQL provider cutover remains unsafe until a guarded replacement passes isolated PG17 tests.

**Threat-model distinction:** [ADR-0025](../adr/ADR-0025-proposed-mvp-trusted-backend-threat-model.md) is pending. Option B would intentionally forgo a database-verifiable actor proof and accept a stolen-runtime-credential impersonation threat, not merely simplify cryptography while preserving every guarantee. No SQL function authorization implementation or grant cutover may rely on Option B until reviewed/ratified and all other gates are satisfied.
