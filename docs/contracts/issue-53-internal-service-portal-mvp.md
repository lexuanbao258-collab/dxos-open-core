## 2. Shared rules and ownership

The Portal is an independent HTTP consumer. For **CREATE**, the future Backend Application must: (1) verify OIDC issuer/subject; (2) classify visibility and tenant membership from authoritative resource context without disclosing it; return indistinguishable HIDDEN/404 before any protected materialization; (3) require explicit CREATE grant **and** the exact verified `workflow:create` authority; (4) only then check the exact active definition/resource binding and load the authoritative immutable definition; (5) perform a final post-guard ACL check inside the write transaction before commit. Do not preload, cache or query the definition or private binding before authorization. If a new resource cannot be classified without a side-effecting write, CREATE remains **BLOCKED** until a safe preauthorization design is reviewed. The present #23 Phase 1 policy seam expects a definition object and does not itself prove this complete ordering or transactional guard.

Workflow alone supplies current state, lifecycle, runtime version and successful transition history. Business facts must not independently assert a contradictory `status`; a read model can join them after resource-scoped authorization. Activation keeps version **0**; PR #63 performs create and activation inside one Application command, with no separate Portal activation route. Each successful transition increments version once; `expectedVersion` is the snapshot version submitted, never a client-selected target state. Definition changes require a new version; running instances remain pinned. PR #63 generates the request UUID and opaque 192-bit Workflow ID server-side and rejects unknown create fields, including caller `instanceId`; the old foundation DTO is not this Application contract. There is no generic reopen, timer, SLA, guard script, notification or attachment transaction in Core.

Business roles below are **eligibility predicates**, not JWT authorities. For **READ/HISTORY, ACTIVATE and TRANSITION**, verify identity, classify authoritative instance/resource visibility before disclosure, then require the operation's own exact authority (`workflow:read`, `workflow:activate`, `workflow:transition` respectively), explicit resource/action ACL and applicable business predicate. Internal authorization lookup may use only the minimum authoritative reference needed to classify visibility; it must not expose snapshots, history, existence or private binding to the caller or materialize a definition before authorization. Use the persisted binding for these operations after access is granted. Do **not** impose CREATE binding checks or an unrelated READ grant on ACTIVATE/TRANSITION. Writes need their final ACL check in the write transaction; prechecks alone do not settle revoke races. Canonical actor is derived server-side from verified issuer and subject; client body/header/display name never supplies actor, requester or ACL. The **original requester** is an Application business fact, distinct from ACL resource owner. Neither requester nor owner bypasses explicit ACL or exact JWT authority. Assignee, processor and confirmer are checked against authoritative business facts and verified principal; assignment targets an eligible tenant member. A changed assignee or revoked grant invalidates subsequent action. List/detail/history must filter at the backend before returning protected data. A visible resource without permission is 403; hidden, cross-tenant or nonexistent resources have indistinguishable 404 status/body; missing/invalid/expired authentication is 401 before protected lookup; unavailable authorization fails closed with sanitized non-success (current Gateway bridge candidate: 503). UI button visibility is advisory only.

The generic operation separation above does not remove Application response permissions: **PR #63 also requires exact `workflow:read` and read ACL on mutations because they return a protected `RequestView`**. CREATE requires exact create + activate + read authorities, active tenant membership, provisioned submitter eligibility and active binding; its SQL explicitly creates resource grants. Specifically, `helpdesk_open` preauthorizes new-resource creation from tenant submitter eligibility, checks the binding, then inserts resource grants before definition materialization. Whether that preauthorization source/order satisfies DEC-D2-04's explicit CREATE grant requirement is **POLICY OPEN / BLOCKED** for Bảo/Yến; B06 does not ratify it. Ownership alone proves no operation permission.

## 7. Transaction and consistency decision for review

**Existing guarantee:** Workflow persistence port owns an authoritative, confirmed durable state/history write per operation; successful return follows COMMIT (ADR-0023). The Request prototype's JPA transaction covers only its Request row/history, not Application+Generic Workflow. **PR #63 implemented candidate:** `HelpdeskService` invokes `PostgresWorkflowPersistence.guardedTransaction`; final authorization/tenant locking, business facts, resource/ACL binding and guarded Workflow SQL use the same physical JDBC connection and one confirmed commit. Resolution rolls back with a failed transition; create includes activation and binding. This is a concrete Application transaction, not an outer Spring transaction pretending to extend an already committed port call. It introduces no Core port change or object-store atomicity. Approval of provisioning, SQL dependency/privileges and final business/recovery policy remains **BLOCKED**.

Validate input without side effects, authorize from verified identity and authoritative sources before protected business writes, and retain final checks/locks through commit. Candidate policy-mutator locks coordinate eligibility/ACL changes with writes; neither a precheck nor a previously returned allowed action settles revocation. Bảo owns the transaction/provisioning contract; Yến maps both independent revocation variants to reviewed evidence. The earlier speculative pending-facts design is not the PR #63 implementation. No operation receipt or idempotency API is promised; a client operation identifier has no security meaning.

For `COMMIT_OUTCOME_UNKNOWN` or a lost response, retain the exact attempted proposal and use **authorized** `loadInstance`/`loadHistory` evidence already provided by the port: for create compare the full initial snapshot, definition binding and resource (an identical instance does not prove which writer created it); for activation compare the full snapshot/lifecycle, since version remains zero and later transitions may advance it; for transition compare the exact proposed record at its resulting version and subsequent authoritative history/snapshot. Separate reads may straddle concurrent changes and must be repeated when needed. A missing/old snapshot or ambiguous matching data does not prove rollback or ownership of the write. If the outcome cannot be established, keep it **UNKNOWN**, use adapter/operator reconciliation, and neither retry blindly nor report success. An explicit new attempt requires a settled prior outcome and fresh authorization/concurrency decision. Attachment upload, if later approved, needs separate provisional-object cleanup and must not claim atomicity with PostgreSQL. The Application persistence/recovery design must be reviewed before LIVE use; it does not require a new Core port or unrelated business feature.

For Portal, reconciliation uses only authorized candidate Detail/History, never Core/DB access. A lost create response may leave the server-generated ID unknown; no receipt/recovery lookup is defined. Partial projections or a matching listed request cannot prove the exact write. Keep UNKNOWN and require authorized operator reconciliation when evidence is insufficient; final recovery procedure/UX remains **POLICY OPEN / BLOCKED** despite focused unknown-commit test evidence.
