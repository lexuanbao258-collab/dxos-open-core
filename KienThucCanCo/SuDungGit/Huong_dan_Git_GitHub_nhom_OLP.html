Git & GitHub — Cẩm nang làm việc nhóm cho OLP

Tài liệu từ số 0 đến làm việc nhóm thực tế: quản lý source code, tài liệu, branch, Pull Request, conflict, hoàn tác, .gitignore, Git LFS, bảo mật và workflow dành riêng cho nhóm 3 người.

Git từ cơ bản → nâng cao Workflow nhóm 3 người Có ví dụ lệnh thực tế Dùng khi thi OLP

Mục tiêu của tài liệu

Sau khi học xong, cả nhóm có thể tự tạo repository chung, chia việc bằng branch, đồng bộ code, tạo Pull Request, review, xử lý conflict và khôi phục khi lỡ thao tác sai — không cần gửi code qua Messenger/Zalo rồi copy đè vào project.

1. Bắt đầu: Git là gì và GitHub là gì?

Git

Hệ thống quản lý phiên bản phân tán. Git theo dõi lịch sử thay đổi của file và cho phép nhiều người phát triển song song.

GitHub

Dịch vụ lưu repository Git trên Internet, có Pull Request, Issues, Actions, Releases, quyền thành viên và nhiều công cụ cộng tác.

Repository

Một “kho dự án” chứa source code, tài liệu và toàn bộ lịch sử Git của dự án.

Nhớ ngắn gọn: Git = công cụ quản lý phiên bản. GitHub = nơi lưu/chia sẻ repository Git online. Có thể dùng Git mà không cần GitHub.

Git giải quyết vấn đề gì?

  • Biết ai sửa gì, lúc nào, tại sao.
  • Quay về phiên bản cũ khi code mới làm hỏng hệ thống.
  • Ba người làm ba phần song song mà không phải copy project qua lại.
  • So sánh thay đổi trước khi nhập vào code chung.
  • Lưu cả source code và tài liệu Markdown, SQL, cấu hình Docker, sơ đồ...
  • Tạo phiên bản nộp bài rõ ràng bằng tag/release.

2. Cài Git và cấu hình lần đầu

Kiểm tra Git đã cài chưa

git --version

Nếu máy trả về kiểu git version 2.x.x là được. Windows có thể cài Git for Windows; macOS có thể dùng Xcode Command Line Tools hoặc Homebrew.

Cấu hình tên và email

git config --global user.name "Ten cua ban"
git config --global user.email "email@example.com"

git config --global --list

Thông tin này đi vào metadata của commit. Nên dùng email gắn với tài khoản GitHub để commit hiển thị đúng người.

Đặt branch mặc định là main

git config --global init.defaultBranch main

3. Các khái niệm Git bắt buộc phải biết

Working Directory

Thư mục bạn đang sửa file trên máy.

Staging Area

Vùng “chờ commit”. git add chọn thay đổi nào sẽ vào commit tiếp theo.

Repository

Nơi Git lưu các commit và lịch sử dự án.

Commit

Một ảnh chụp (snapshot) của trạng thái dự án tại một thời điểm.

Branch

Nhánh phát triển độc lập. Dùng để làm tính năng mà không phá code chính.

Merge

Gộp lịch sử/thay đổi từ một branch vào branch khác.

Remote

Repository ở máy chủ khác, thường là GitHub. Tên mặc định hay dùng: origin.

Pull Request

Yêu cầu đưa thay đổi của branch vào branch đích, có review và thảo luận.

Conflict

Xảy ra khi Git không tự quyết định được phải giữ phiên bản thay đổi nào.

Ba vùng quan trọng trong Git

Working Directory
sửa file
Staging Area
git add
Local Repository
git commit
GitHub / Remote
git push

Nhiều người mới tưởng git add là “upload”. Không phải. git add chỉ đưa thay đổi vào Staging Area trên máy của bạn. Upload lên GitHub là git push.

4. Tạo hoặc lấy một repository

Cách A — Tạo dự án Git từ thư mục đang có

cd duong-dan-den-project
git init
git status

Sau git init, Git tạo thư mục ẩn .git. Đây là “bộ não” lưu lịch sử repository.

Cách B — Clone repository từ GitHub

git clone https://github.com/USERNAME/REPOSITORY.git
cd REPOSITORY
git remote -v

Clone chỉ làm một lần. Những ngày sau không clone lại; dùng git pull để cập nhật code.

Kết nối thư mục local với GitHub

Lưu ý trước khi kết nối: nếu project local đã có commit đầu tiên, cách an toàn nhất là tạo repository GitHub trống hoàn toàn (không README, .gitignore, license). Khi đó hai bên có cùng một lịch sử bắt đầu.

git remote add origin https://github.com/USERNAME/REPOSITORY.git
git branch -M main
git remote -v
git push -u origin main

-u thiết lập upstream để lần sau có thể chỉ gõ git push và git pull.

Nếu GitHub repository đã được tạo kèm README.md, local và remote có thể có hai lịch sử ban đầu khác nhau. Với người mới, đừng cố “ép push”: hãy git clone <url>, rồi đưa source code vào thư mục đã clone, kiểm tra bằng git status và commit. Cách này dễ hiểu, an toàn hơn.

5. Kết nối máy tính với GitHub

Git và GitHub là hai hệ thống khác nhau. Để push/pull repository private hoặc thao tác cần quyền, máy tính cần xác thực với GitHub. Không dùng password tài khoản GitHub làm mật khẩu Git qua HTTPS.

Cách A — HTTPS (dễ bắt đầu)

https://github.com/USERNAME/REPOSITORY.git
git remote -v

HTTPS có thể xác thực bằng Git Credential Manager, GitHub CLI hoặc Personal Access Token (PAT) khi cần. GitHub không còn hỗ trợ xác thực Git bằng password tài khoản; hãy để Credential Manager xử lý đăng nhập thay vì ghi token vào source code hay tài liệu.

Cách B — SSH

ssh-keygen -t ed25519 -C "email@example.com"

# Windows Command Prompt
type %USERPROFILE%\.ssh\id_ed25519.pub

# PowerShell
Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub

# macOS/Linux
cat ~/.ssh/id_ed25519.pub

Chép public key (đuôi .pub) vào GitHub, rồi kiểm tra:

ssh -T git@github.com

# Remote SSH
git@github.com:USERNAME/REPOSITORY.git

# Đổi remote HTTPS sang SSH
git remote set-url origin git@github.com:USERNAME/REPOSITORY.git

HTTPS dễ bắt đầu hơn; SSH tiện nếu bạn dùng Git thường xuyên. Không cần cả nhóm bắt buộc dùng cùng một cách, miễn git remote -v trỏ đúng repository và mỗi người xác thực được.

7. Commit đúng cách

Một commit tốt nên như thế nào?

  • Mỗi commit tập trung vào một thay đổi logic.
  • Code tại commit đó nên build/chạy được nếu có thể.
  • Message nói rõ mục đích thay đổi.
  • Không gom một tuần code vào một commit tên update.

8. Branch — nền tảng làm việc nhóm

Các lệnh branch chính

# Xem branch
git branch
git branch -a
git branch --show-current

# Tạo + chuyển branch
git switch -c feature/login

# Hoặc cú pháp cũ
git checkout -b feature/login

# Chuyển branch
git switch main

# Xóa branch local sau khi merge
git branch -d feature/login

git switch là cú pháp mới, dễ đọc và nên ưu tiên cho người mới: git switch main, git switch -c feature/login. git checkout là cú pháp cũ nhưng vẫn rất phổ biến trong tutorial; nó còn làm nhiều việc khác nên dễ gây nhầm lẫn. Vì vậy tài liệu này ưu tiên switch và restore, nhưng vẫn ghi checkout để bạn đọc được tài liệu cũ.

Cách đặt tên branch

Mục đíchGợi ý
Tính năngfeature/login, feature/order-api
Sửa lỗifix/login-validation
Tài liệudocs/system-design
DevOpsdevops/docker-compose, ci/github-actions

Nhóm nhỏ không cần GitFlow phức tạp. Chỉ cần main ổn định + branch theo nhiệm vụ + Pull Request là đủ tốt cho OLP.

Ví dụ thực tế — Người 1 làm chức năng đăng nhập

# 1) Luôn bắt đầu từ main mới nhất
git switch main

# 2) Tạo branch cho nhiệm vụ
git switch -c feature/login

# 3) Code...
git status

# 4) Commit

# 5) Push branch

Sau đó vào GitHub tạo Pull Request từ feature/login → main. Một thành viên khác kiểm tra trước khi merge.

Luật bảo vệ main

Nên làm

  • main luôn chạy được.
  • Mỗi việc có branch riêng.
  • Merge qua Pull Request.
  • Ít nhất một người khác review thay đổi quan trọng.

Tránh

  • Ba người cùng push trực tiếp main.
  • Branch cá nhân sống hàng tuần không đồng bộ.
  • Merge khi chưa test.
  • Copy project của nhau rồi ghi đè.

Bảo vệ branch main trên GitHub

“Không push trực tiếp vào main” chỉ là quy ước miệng. Nếu repository phù hợp, hãy biến nó thành luật kỹ thuật bằng GitHub Rules / Branch Protection cho branch main.

Developer
Feature branch
Pull Request
Review
CI / Status Check
Merge
main
  • Require Pull Request before merging.
  • Require approvals (nhóm 3 người thường bắt đầu với 1 approval).
  • Require status checks sau khi đã có CI.
  • Block/restrict force pushes và không cho xóa branch main.

GitHub có thể hiển thị “Rules”, “Rulesets” hoặc “Branch protection” tùy giao diện/quyền repository. Không cần cấu hình enterprise phức tạp: chỉ cần bảo vệ main để PR, review và CI thực sự có ý nghĩa.

10. Đồng bộ code giữa các thành viên

fetch khác pull

LệnhÝ nghĩa
git fetchTải thông tin/commit mới từ remote nhưng chưa nhập vào branch hiện tại.
git pullFetch + tích hợp thay đổi vào branch hiện tại.
# Chỉ tải thông tin/commit mới về local, chưa nhập vào branch hiện tại
git fetch origin

# Ví dụ tích hợp rõ ràng, dễ kiểm soát cho người mới
git merge origin/main

# Hoặc pull bằng merge, không rebase
git pull --no-rebase origin main

Về bản chất, git pull thường là fetch + integrate; phần integrate có thể là merge hoặc rebase tùy cấu hình/cách gọi. Vì vậy khi cần thận trọng, dùng fetch trước để biết mình sắp nhập gì.

Cập nhật branch đang làm từ main

git switch main
git pull origin main

git switch feature/login
git merge main

Nếu merge không conflict, branch feature/login đã có code mới nhất của nhóm.

Nên đồng bộ thường xuyên. Đừng chờ 5 ngày rồi mới merge main; conflict sẽ khó hơn rất nhiều.

Khi push bị rejected

Thông báo non-fast-forward thường có nghĩa remote đã có commit mới mà máy bạn chưa có. Không phải lúc nào cũng nên gõ git pull một cách mù quáng. Trước hết cần biết đang ở branch nào và remote nào.

git branch --show-current
git status
git remote -v

# Sau khi xác nhận đang cần đồng bộ main:
git fetch origin
git merge origin/main

# xử lý conflict nếu có, rồi mới push
git push

Nếu bạn đang ở feature branch, đừng tự động nhập một branch không rõ nguồn. Đọc thông báo lỗi, xem lịch sử local/remote và chọn branch cần tích hợp. Chỉ dùng force push khi hiểu rõ tình huống; không dùng để “chữa” non-fast-forward trên main hay branch chung.

11. Pull Request và Code Review

Pull Request dùng để làm gì?

  • Cho cả nhóm xem diff trước khi code vào main.
  • Thảo luận, đặt câu hỏi, yêu cầu sửa.
  • Ghi lại lịch sử “tính năng này do ai đưa vào và vì sao”.
  • Có thể gắn Issue, CI test, reviewer và checklist.

Mẫu mô tả Pull Request

## Thay đổi
- Thêm API POST /api/auth/login
- Thêm AuthService
- Thêm validation email/password

## Cách kiểm tra
1. Chạy backend
2. Gửi POST /api/auth/login
3. Kiểm tra response 200 và token

## Lưu ý
- Cần biến môi trường JWT_SECRET
- Không commit file .env

Checklist review

  • Code có đúng yêu cầu nhiệm vụ không?
  • Có file bí mật / dữ liệu thừa không?
  • Tên biến, tên hàm và cấu trúc dễ hiểu?
  • Có xử lý lỗi cơ bản?
  • Có phá API/chức năng phần khác không?
  • Đã chạy test/build?
  • README/docs có cần cập nhật?

12. Merge, Squash merge và Rebase

Merge commit

Giữ nguyên lịch sử của branch feature, phù hợp khi muốn thấy rõ nhánh đã phát triển như thế nào.

A---B---C main
     \
      D---E feature

       ↓ merge

A---B---C------M
     \        /
      D------E

Squash merge

Gộp nhiều commit của feature thành một commit trên main. Hợp lý khi branch có các commit tạm như fix, fix again, update, test nhưng kết quả cuối chỉ là một thay đổi rõ ràng.

Rebase cơ bản

Rebase đặt lại chuỗi commit feature lên trên base mới, làm lịch sử thẳng hơn nhưng có thể viết lại lịch sử commit. Không rebase tùy tiện branch chung đã được nhiều người dùng; với nhóm mới, merge qua Pull Request thường dễ an toàn hơn.

13. Cherry-pick một commit cụ thể

Dùng khi cần lấy một commit từ branch khác vào branch hiện tại.

feature-a: A — B — C
feature-b: D — E

# đang ở feature-b, muốn lấy commit B
git cherry-pick <hash-B>

Cherry-pick là công cụ tình huống, không thay cho workflow merge/PR thông thường. Dùng nhiều có thể làm lịch sử khó theo dõi hoặc tạo commit trùng nội dung.

14. GitHub Actions / CI là gì?

CI (Continuous Integration) tự build/test khi bạn push code hoặc tạo Pull Request, giúp phát hiện lỗi trước khi merge.

Push code
GitHub Actions
Build
Test
Pass / Fail
Review + Merge

Ví dụ tham khảo cho Java Gradle, lưu thành .github/workflows/ci.yml:

name: CI

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'

      - uses: gradle/actions/setup-gradle@v4

      - run: ./gradlew build

Đây chỉ là CI build/test cơ bản, không phải cấu hình deployment. Sau khi workflow chạy ổn, có thể đặt status check của CI thành điều kiện merge vào main.

15. Merge conflict — hiểu và xử lý

Conflict xảy ra khi nào?

Ví dụ hai người đều sửa cùng vùng trong README.md. Git không biết nên chọn phiên bản A hay B nên dừng lại để người quyết định.

Dấu conflict trong file

<<<<<<< HEAD
Nội dung trên branch hiện tại
=======
Nội dung từ branch đang merge
>>>>>>> main

Bạn phải sửa file thành nội dung cuối cùng mong muốn, đồng thời xóa ba dòng marker <<<<<<<, =======, >>>>>>>.

Quy trình xử lý

Hãy nhìn dòng trạng thái của Git để biết bạn đang resolve conflict của merge hay rebase; bước kết thúc khác nhau.

Trường hợp merge

git status

# Mở file conflict, sửa nội dung cuối cùng và xóa marker
git add <file-da-sua>
git commit
# hoặc, tùy tình huống Git yêu cầu
git merge --continue

# Muốn hủy toàn bộ merge đang dở
git merge --abort

Trường hợp rebase

git status

# Mở file conflict, sửa nội dung cuối cùng và xóa marker
git add <file-da-sua>
git rebase --continue

# Muốn hủy toàn bộ rebase đang dở
git rebase --abort

Sau khi thao tác hoàn tất và kiểm tra lại, mới git push. git add . rồi git commit không phải workflow áp dụng y hệt cho mọi loại conflict.

Không chọn “Accept Current” hay “Accept Incoming” một cách mù quáng. Có trường hợp phải giữ cả hai phần hoặc viết lại thành phiên bản thứ ba.

16. Hoàn tác khi làm sai

Bỏ thay đổi chưa commit

git status

# Khôi phục thay đổi của một file tracked trong working tree
git restore path/to/file

# Khôi phục thay đổi của các file tracked trong working tree
git restore .

git restore . khôi phục thay đổi ở file tracked; nó không tự xóa file untracked mới tạo.

UserService.java
Tracked + modified
→ git restore . có thể khôi phục.

test.txt
Untracked
→ git restore . không xóa file này.

git restore có thể làm mất code chưa commit. Luôn xem git status trước và chắc chắn bạn thực sự không cần các thay đổi tracked đó.

Đã git add nhưng chưa muốn commit

git restore --staged path/to/file

Lệnh này chỉ đưa file ra khỏi staging; thay đổi trong working tree vẫn còn.

Sửa commit cuối cùng chưa push

git add file-bi-thieu
git commit --amend

# Hoặc đổi message
git commit --amend -m "feat: add login API and validation"

Đã push commit xấu — ưu tiên revert

git log --oneline
git revert <commit-hash>
git push

revert tạo một commit mới đảo ngược commit cũ nên an toàn hơn trong repository có nhiều người.

reset — mạnh và cần cẩn thận

LệnhKết quả
git reset --soft HEAD~1Bỏ commit cuối, giữ thay đổi ở staging.
git reset HEAD~1Bỏ commit cuối, giữ file thay đổi nhưng unstaged.
git reset --hard HEAD~1Bỏ commit và bỏ luôn thay đổi file.

Nhóm mới học Git không nên dùng git reset --hard hoặc git push --force trên branch chung nếu chưa hiểu hậu quả.

Nếu thực sự phải force push một branch cá nhân sau khi đã hiểu lịch sử bị viết lại, ưu tiên:

git push --force-with-lease

--force-with-lease có thêm kiểm tra để giảm nguy cơ ghi đè commit mới trên remote. Dù vậy, người mới không force push vào main hoặc branch chung.

Cứu commit tưởng đã mất bằng reflog

reflog ghi lại các lần HEAD di chuyển trên máy local và rất hữu ích khi reset nhầm.

git reflog

# Ví dụ tìm thấy:
abc1234 HEAD@{3}: commit: feat: add login API

# Kiểm tra commit trước khi cứu
git show abc1234

# Tạo branch an toàn trỏ vào commit đó
git switch -c recovery-branch abc1234
Reset nhầm
   ↓
git reflog
   ↓
Tìm commit hash cũ
   ↓
git show <hash>
   ↓
git switch -c recovery <hash>
   ↓
Code được cứu

Reflog chủ yếu là lịch sử local, không phải bản sao lưu vĩnh viễn trên GitHub. Khi đã tìm được code quan trọng, hãy kiểm tra, commit/push branch recovery để bảo toàn nó.

git clean — chỉ dùng khi hiểu rõ

# Luôn xem trước file/thư mục sẽ bị xóa
git clean -n

# Chỉ sau khi đã kiểm tra kỹ
git clean -fd

git clean -fd có thể xóa file untracked khỏi ổ đĩa và rất khó khôi phục. -f là force, -d gồm cả thư mục. Người mới không nên chạy lệnh này nếu chưa xem kết quả git clean -n.

Bảng lệnh cần cẩn thận

LệnhMức độRủi ro
git restore .Cẩn thậnMất thay đổi tracked chưa commit.
git reset --hardNguy hiểmMất thay đổi local.
git clean -fdRất nguy hiểmXóa untracked files.
git push --forceRất nguy hiểmGhi lại remote history.
git branch -DCẩn thậnXóa branch chưa merge.

Nếu chưa chắc chắn, chạy git status và tạo commit/branch backup trước.

5 lệnh kiểm tra trước khi hoảng
git status
git branch --show-current
git remote -v
git log --oneline --graph --decorate -10
git reflog -10

Đừng chạy ngay git reset --hard, git clean -fd hoặc git push --force khi chưa hiểu nguyên nhân.

17. Stash — cất tạm code đang làm

Bạn đang sửa dở nhưng phải chuyển branch để xử lý việc gấp:

# git stash thường không gồm file untracked
git stash push -u -m "WIP login form"
git switch main

# Quay lại
git switch feature/login
git stash list
git stash show
git stash pop

git stash apply áp dụng nhưng giữ stash. git stash pop áp dụng stash vào working tree và thường xóa stash đó nếu áp dụng thành công; khi có conflict, stash có thể vẫn còn. Dùng git stash drop để xóa stash mà không apply.

Stash là tạm thời, không phải nơi lưu công việc dài hạn. Nếu thay đổi có giá trị rõ ràng, commit trên branch riêng thường dễ quản lý hơn.

Nếu secret đã từng push lên GitHub, việc xóa file ở commit mới không làm secret cũ biến mất khỏi lịch sử. Hãy đổi/revoke secret ngay.

19. Bảo mật khi dùng GitHub

Tuyệt đối không commit

  • Mật khẩu database.
  • API key / access token.
  • Private key.
  • File .env thật.
  • Thông tin đăng nhập cloud.

Nên làm

  • Dùng environment variables.
  • Commit .env.example chứa tên biến và giá trị mẫu không bí mật để người khác biết cần cấu hình gì.
  • Dùng GitHub Secrets cho CI/CD.
  • Rotate secret nếu lỡ lộ.
# .env.example
DB_HOST=localhost
DB_PORT=5432
DB_NAME=your_database
DB_USER=your_user
DB_PASSWORD=your_password
JWT_SECRET=change_me

Ví dụ trên chỉ dùng placeholder. Tuyệt đối không đưa credential, token, mật khẩu hoặc secret thật vào .env.example.

Nếu secret từng được push: xóa file không đủ. Hãy (1) revoke/rotate secret, (2) sửa cấu hình đang dùng secret đó, (3) loại secret khỏi tracking, và chỉ khi cần mới làm sạch history. Không đưa token thật vào issue, PR, chat hay ví dụ.

20. Quản lý tài liệu chung trên Git

Tài liệu dạng text/Markdown phù hợp với Git nhất vì Git hiển thị diff rất rõ.

docs/
├─ 01-requirements.md
├─ 02-use-cases.md
├─ 03-architecture.md
├─ 04-database-design.md
├─ 05-api-documentation.md
├─ images/
└─ presentation/

Nếu tài liệu là Word/PowerPoint/PDF thì Git vẫn lưu được, nhưng diff không đẹp bằng text. Hãy tránh để nhiều người cùng sửa một file nhị phân lớn cùng lúc.

21. File lớn và Git LFS

Video demo, file thiết kế hoặc binary lớn làm repository nặng. Không phải file lớn nào cũng nên cho vào Git; video demo lớn thường nên cân nhắc Drive hoặc nền tảng lưu file phù hợp. Nếu buộc phải lưu file lớn trên GitHub, có thể cân nhắc Git LFS.

git lfs install
git lfs track "*.mp4"
git add .gitattributes
git add demo.mp4
git commit -m "docs: add demo video with Git LFS"
git push

Trước khi dùng LFS, kiểm tra giới hạn dung lượng/quota của tài khoản. Phải commit file .gitattributes; file này cho Git biết loại nào được theo dõi bằng LFS.

30. Tự kiểm tra kiến thức

Git và GitHub có phải cùng một thứ không?

Không. Git là hệ thống quản lý phiên bản; GitHub là dịch vụ lưu repository Git và hỗ trợ cộng tác.

git add có đưa code lên GitHub chưa?

Chưa. git add chỉ đưa thay đổi vào staging local. Muốn lên GitHub phải commit rồi git push.

Clone và pull khác nhau thế nào?

clone tạo bản sao repository lần đầu. pull cập nhật repository đã có.

Tại sao không nên code trực tiếp trên main?

Vì một thay đổi chưa hoàn thiện có thể phá phiên bản chung. Branch tạo vùng làm việc riêng và PR tạo điểm kiểm tra trước khi merge.

Khi nào nên dùng git revert?

Khi commit xấu đã được chia sẻ/push. Revert tạo commit đảo ngược nên không viết lại lịch sử chung.

File .env lỡ push rồi xóa có đủ không?

Không. Secret có thể vẫn tồn tại trong lịch sử. Phải rotate/revoke secret và cân nhắc làm sạch lịch sử nếu cần.

Cả ba người có nên dùng một branch chung không?

Không nên cho công việc thường ngày. Tốt hơn mỗi nhiệm vụ có branch riêng; cùng lắm mỗi người có branch tạm nhưng branch theo tính năng vẫn dễ review và merge hơn.

Tại sao GitHub hỏi đăng nhập khi push?

Máy đang cần xác thực với GitHub, nhất là với HTTPS hoặc repository private. Dùng Git Credential Manager, GitHub CLI, PAT khi cần hoặc SSH key; không nhập password tài khoản GitHub làm password Git HTTPS.

Tôi đã thêm file vào .gitignore nhưng Git vẫn theo dõi?

.gitignore không tự bỏ theo dõi file đã tracked. Dùng git rm --cached <file>, rồi commit thay đổi.

Tôi reset nhầm thì làm gì?

Dừng thao tác phá hủy thêm, chạy git reflog, kiểm tra hash bằng git show <hash>, rồi tạo recovery branch bằng git switch -c recovery <hash>.

Tôi đang ở branch nào và đang kết nối GitHub nào?

Dùng git branch --show-current để xem branch hiện tại; dùng git remote -v để xem URL remote.

Push báo non-fast-forward thì có được force push không?

Không nên. Kiểm tra branch, remote và lịch sử local/remote; dùng git fetch origin rồi tích hợp đúng branch. Không force push vào main hoặc branch chung để chữa lỗi này.

Commit có lên GitHub chưa?

Chưa. Commit chỉ ở local cho đến khi bạn chạy git push.
